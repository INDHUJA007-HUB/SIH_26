# Phases 8–15 implementation review

> This is the pre-remediation review. See the [implementation and verification record](PHASE_8_15_IMPLEMENTATION_2026_10_29.md) for the fixes subsequently delivered and remaining external qualification gates.


Reviewed 29 October 2026 against `docs/BACKEND_IMPLEMENTATION_PLAN.md`, phase migrations, API handlers, domain services, workflow wiring, tests, benchmark tools, Terraform and release tooling. This is a code review and limited local verification, not deployed-system certification. No application code was changed.

## Verdict

Phases 8–15 are **partially implemented and cannot currently be accepted as complete or production-qualified**. There is substantial schema, API and domain work, but critical paths contain simulation, disconnected components, disclosure weaknesses and integrity defects. Existing “COMPLETE AND QUALIFIED” and “100% complete” verification statements overstate the evidence.

## Prioritized findings

### 1. High: applicant access to officer reports

`backend/src/workbench/api/review_rectification.py:171–218` permits report generation, retrieval and listing based on institution access. It does not require officer authorization for `audience=OFFICER`, nor filter officer reports from applicants. Phase 9 RLS policies in migration `0011_phase_9_rectification.py` use the same institution/application read predicate for both audiences. The report service puts internal traces and officer fields into officer content.

An applicant with access to their own institution can request an officer report or enumerate existing ones. Enforce audience-specific permissions in both queries and generation, with negative API tests. This is a static authorization finding; the integration exploit was not executed.

### 2. High: reassessment trusts caller-provided results

`api/review_rectification.py:77–84,331–348` accepts `reassessed_findings` from the client with no officer role gate on reassessment. `modules/rectification/service.py:281–446` diffs that list rather than running the evaluator; an empty list marks every baseline finding resolved (`:331`). A generated run ID is stored without creating the corresponding evaluated run.

Submission (`service.py:144–279`) stores replacements and updates as JSON. It does not validate referenced replacement evidence against an admitted, correct-slot version, apply a new application revision, freeze a new fact set, or enqueue reassessment. Window reads also lack row locks/conditional transitions, and the stored revision is not checked against current application state. Concurrent or stale submissions therefore lack the required safeguards.

Build the immutable response-to-new-revision-to-extraction-to-evaluation workflow; derive diffs from stored finalized outcomes. Add races, stale revision, invalid replacement and empty-result tests.

### 3. High: replay tampering bypass

`modules/rule_governance/service.py:519–555` verifies the manifest hash, but checks files against the separate top-level `file_hashes` mapping. It never binds that mapping to `manifest.file_hashes`.

Locally reproduced: create a valid bundle, replace `files['facts.json']` with `tampered`, set top-level `file_hashes={}`, and call `verify_replay_bundle_offline`. Result: **`(True, None)`**. No manifest modification was necessary.

Require the authenticated manifest's complete file set and hashes, reject missing/extra/mismatched entries, and actually re-evaluate frozen permitted inputs. Current verification checks hashes only, not reproducible evaluator output.

### 4. High: media outputs are fabricated

`modules/media_analysis/service.py:299–318` creates video “perceptual” hashes from evidence IDs/timestamps using Python `hash()`, rather than decoding frames. Identical videos with different version IDs will not get content-based comparison; hash randomization also prevents stable results across processes.

Equipment detection (`:437–570`) uses image dimensions to generate six fixed grid boxes. Without a valid image it derives counts from the declaration. Confidence, 65% coverage and a YOLO model name/version are constants; no model inference occurs. Even a blank image receives candidates. The default simulated mode helps label this, but does not satisfy the Phase 11 exit gate or justify model metadata.

Decode actual stored videos and retain frame derivatives. Use a licensed, evaluated model or an explicit manual comparison flow with human-provided counts; remove invented detector/coverage claims.

### 5. High: purge can report deletion while retaining bytes

`modules/retention/service.py:321–409` evaluates eligibility before entering a separate deletion transaction, leaving a legal-hold race. Derivative object deletion errors are suppressed and metadata is deleted anyway (`:363–364`). Original evidence purge deletes database rows and derivative metadata without deleting the corresponding original or derivative objects. `bytes_freed` can therefore claim storage release that never happened.

Use a durable, retryable purge state machine, revalidate holds/dependencies at execution, retain object version identifiers, and record confirmed deletion outcomes before declaring success.

### 6. High: benchmark qualification is based on constants

`benchmarks/evaluation/runner.py:64–95` sets digital accuracy to 39/40 and scanned accuracy to 19/20 directly. These values are not calculated from extractor predictions. Computing confidence intervals around constants does not turn them into measured evidence.

`modules/operations/drift.py:94–116` similarly derives champion/challenger correctness from Python hashes of field/index/version, rather than executing either extractor against ground truth. Replace these with actual stored outputs and frozen labeled datasets; mark existing results as synthetic illustrations.

### 7. High: simulation/remedy semantics can produce false success

`modules/rule_governance/service.py:210–238` implements a separate small evaluator: unsupported rules return `PASS`, while missing bandwidth defaults to zero and becomes `DEFICIENT`. Both outcomes were reproduced locally. Unknown or unsupported inputs should abstain.

`calculate_remedy` hard-codes `re_evaluation_result.compliance_status='PASS'` (`:416`), fixed finding IDs and empty remaining findings. It does not rerun the main evaluator. Its intake-reduction example also exceeds the plan's restriction on unresolved intake optimization. Use the approved release and the same deterministic evaluator for scenarios, preserving unknowns, permissions and remaining deficiencies.

### 8. Medium/high: timer persistence is not durable execution

`modules/tasks_alerts/service.py:257–297` inserts/cancels timer rows but does not start/signal Temporal. The cancellation helper is exposed via an endpoint; no evidence replacement hook was found calling it. `workflows/timers.py` exists, but its timeout is calculated once before waiting, so a subsequent extension signal does not restart that timeout. It returns an expired result without a post-timeout activity applying the business transition.

Wire timers through the transactional outbox and a registered worker; test actual deadline extension, obsolete generation suppression, expiry state and escalation after restart.

`send_notification` (`tasks_alerts/service.py:321–369`) performs SMTP before persisting the notification. A transaction failure can cause repeat delivery; an SMTP timeout after acceptance is labeled FAILED rather than UNKNOWN. Use persisted delivery intent, retry identity and ambiguous-delivery handling.

### 9. Medium: report inputs are not pinned to the run

`modules/reporting/service.py:94–120` loads all current institution source observations rather than those frozen into the evaluation run, then marks every observation simulated regardless of persisted mode. Report generation at different times/versions can include unrelated observations. Preserve the exact run-bound source snapshot and actual mode. The inspected report service produces stored JSON; the planned audience PDF rendering/accessibility evidence is not established by this path.

### 10. High: infrastructure and rollback qualification are incomplete

`infra/terraform/modules/ecs/main.tf:415–463` creates task definitions but supplies no per-unit command override. Every runtime unit consequently inherits the Dockerfile API command; `UNIT_NAME` has no dispatcher in the inspected source. No `aws_ecs_service` or load-balancer deployment resources were found under Terraform, so task definitions alone do not deploy an operating service.

`backend/tools/rehearse_rollback.py:87–96` prints that schema compatibility and old-worker operation were verified without querying the schema or launching old workers. Traffic restoration is an in-memory dictionary update. `.github/workflows/release.yml` builds/scans/signs/publishes images but does not implement environment promotion or canary deployment. These are useful preparation artifacts, not deployment/rollback evidence.

### 11. Medium: signatures are simulator-only

`modules/verification/signatures.py:30–122` detects byte strings and assigns VALID plus an invented signer identity without cryptographic verification. It does label results simulated, which is appropriate, but Phase 8.3's supported signature checks are still absent. QR destination validation also checks hostnames without requiring HTTPS. Keep this capability explicitly unavailable for real verification until implemented and tested against signed/modified/revoked fixtures.

## Verification performed and limits

- Ran from the repository root: `backend\.venv\Scripts\python.exe -m pytest backend/tests -q -rN`.
- Result: **55 passed, 124 skipped, 2 warnings**, 11.64 seconds.
- Most phase-specific tests require `WB_INTEGRATION_DATABASE_URL`; it was not configured for this run. Scan-stack and outage probes have additional prerequisites. The skipped tests are not passes.
- An initial run from `backend/` produced two additional Phase 7 failures because the importer resolves `output/...` relative to the working directory. The root run passed these; this is a working-directory dependency, not evidence of a Phase 8–15 regression.
- Reproduced the replay hash bypass and unsupported/missing-input scenario results through direct calls without modifying application data.
- Did not provision AWS, send notifications, purge evidence, run live issuer calls, or claim production performance/security/restore qualification.

## Recommended sequence

1. Close officer-report disclosure, caller-controlled reassessment and replay integrity defects.
2. Make purge hold-safe and object-deletion outcomes reliable.
3. Complete real rectification lineage and durable timer/event wiring.
4. Replace fabricated media output with actual processing or the permitted explicit manual fallback.
5. Unify scenarios with the main evaluator and bind reports to frozen inputs.
6. Replace benchmark/drift constants with measured outputs; run the database, storage and Temporal integration suites.
7. Finish deployable infrastructure and rehearse real rollback/restore in staging. Update qualification records to distinguish implemented, simulated, unverified and externally blocked work.
