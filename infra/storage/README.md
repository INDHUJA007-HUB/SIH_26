# Storage authority and cloud boundary

Local bootstrap configures versioning, AES256 default encryption, public access blocking and one-day incomplete multipart abortion. Moto uses synthetic credentials and cannot qualify cloud IAM, KMS or Object Lock. The reference policy JSON is a reviewed deployment input, **not an applied cloud deployment**. Apply the transport policy separately to both buckets with the correct names; local HTTP intentionally uses no cloud TLS deny policy.

The API signs only quarantine keys, pins object versions and never returns clean URLs. Its HEAD checks require S3 object read permission: AWS does not have a separate HEAD-only IAM action. Before cloud activation, completion must always supply an exact version and use `GetObjectVersion`; a legacy omitted-version completion also needs `GetObject` on quarantine. The template intentionally omits that broader action. A deployed API must reject omitted versions or add the explicitly reviewed permission. Multipart recovery currently also HEADs the unique key's current object after a lost provider acknowledgement; qualify that path under the chosen cloud identity.

Use distinct task identities for API, delivery, scanner and reconciler. The current local storage adapter uses emulator credentials; the cloud adapter/credential wiring and KMS policy belong to Phase 14. No runtime role needs deletion of accepted originals. Restrict bucket policy principals to the deployed roles; enable versioning before receiving any file; configure public blocking and encryption at account and bucket levels; add KMS permissions only for the appropriate producer/consumer. Exact cloud signatures, CORS, checksum rejection and retry recovery must be exercised against the target provider before pilot activation.

Add client-origin CORS only for approved origins and PUT headers, and expose ETag/version response headers. Do not enable wildcard authenticated origins. Lifecycle deletion of accepted evidence is absent until retention and legal-hold owners approve it. Backup/restore must retain historical version identifiers or maintain an explicitly versioned recovery mapping.
